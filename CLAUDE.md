## Project Overview

This is a Flask-based web application for scheduling ministering interviews in LDS church wards. The application manages districts, companionships (teams), interview time slots, and automated notifications via email/SMS.

Key feature: The app can scrape companionship data from the LDS Church's LCR (Leader and Clerk Resources) website using Selenium to automatically import member information.

## Development Commands

### Running the Application

```bash
# Local development
python app.py
# Runs on http://0.0.0.0:8181

# With virtual environment
python -m venv venv
venv\Scripts\activate  # Windows
source venv/bin/activate  # Linux/Mac
pip install -r requirements.txt
python app.py
```

### Database Management

The app uses SQLite by default (`interviews.db` in `instance/` folder). The database is created automatically on first run via `db.create_all()` in the main block.

To reset the database, delete `instance/interviews.db` and restart the app.

### Running the Scraper

The scraper can be run standalone or through the web interface:

```bash
# Standalone scraper (for testing)
python app_scraper.py <username> <password>

# Local scraper with visible browser (for debugging)
python local_scraper.py
```

## Architecture

### Database Models (app.py:39-71)

The application uses five core SQLAlchemy models:

1. **District** - Top-level organizational unit with an interviewer
2. **Team** - Represents a companionship within a district
3. **Member** - Individual members with unique tokens for scheduling
4. **InterviewSlot** - Available time slots with capacity limits
5. **Booking** - Junction table linking members to interview slots

**Important relationships:**
- District → Teams (one-to-many)
- Team → Members (one-to-many)
- InterviewSlot → Bookings (one-to-many with capacity limit)
- Member tokens are unique 32-character hex strings for secure scheduling links

### Web Scraping System (app_scraper.py)

The scraper extracts ministering data from LCR using a two-tier approach:

1. **Primary method**: Extracts data from `__NEXT_DATA__` JSON embedded in the page
   - Located in `<script id="__NEXT_DATA__">` tag
   - Path: `data["props"]["pageProps"]["initialState"]["ministeringData"]`
   - Much faster and more reliable than HTML parsing

2. **Fallback method**: Table scraping with popup interaction
   - Used if JSON extraction fails
   - Opens member popups to extract phone/email
   - Slower but works if page structure changes

**Key functions:**
- `setup_chrome_driver()` - Configures headless Chrome with appropriate options
- `login_to_lcr()` - Handles OAuth login flow and data extraction
- `scrape_ministering_data()` - Main entry point with progress callbacks

### Progress Tracking (app.py:19-21)

Long-running operations (scraping, imports) use thread-safe progress tracking:
- `progress_store` - Global dict storing progress by UUID
- `progress_lock` - Threading lock for safe concurrent access
- Progress callbacks update status, messages, and step counts for frontend polling

### Notification System

Email and SMS notifications are sent via:
- **Email**: Flask-Mail with SMTP (configured for Gmail)
- **SMS**: Twilio integration (optional, requires env vars)
- Notifications send unique scheduling links using member tokens

## Important Implementation Details

### Booking Logic (app.py:426-452)

Team-based slot restrictions:
- Once a slot is booked by one member, only their team members can book the same slot
- This ensures companionships interview together
- Maximum `max_slots` members per slot (default: 10)

### Slot Generation (app.py:362-389)

Recurring slots are generated by:
1. Selecting day of week (0=Monday, 6=Sunday)
2. Defining start time and duration
3. Specifying number of consecutive slots per day
4. Setting number of weeks to generate

### Member Reassignment (app.py:528-586)

Members can be reassigned between companionships:
- Existing bookings are automatically cancelled on reassignment
- Member email is used as unique identifier across reassignments
- Tokens persist through reassignment for continuous access

### Import Workflow

1. Scrape or upload CSV → stores in `progress_store` or session
2. Confirmation page shows preview grouped by district/companionship
3. Optional "Clear existing data" checkbox for fresh imports
4. Import creates/updates districts, teams, and members
5. Members matched by email to prevent duplicates

## Common Issues

**ChromeDriver version mismatch**: The scraper downloads ChromeDriver 141 to match Chrome 141. Update version numbers in `app_scraper.py:54-55` if Chrome updates.

**OAuth login failures**: LCR uses id="username" and id="password" fields. Fallback selectors exist for direct login (id="username-input", id="password-input").

**Popup extraction failures**: Member contact info popups use class "sc-cd0364fd-0" or role="dialog". Check `chromedriver_page.html` for current structure.

**Database locked errors**: SQLite doesn't handle concurrent writes well. Use PostgreSQL for production with multiple workers.
